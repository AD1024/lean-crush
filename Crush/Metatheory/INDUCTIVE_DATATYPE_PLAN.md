# Certified user-defined inductive datatypes

Status: active worklist

This plan extends the certified route

```text
Lean.Expr
  -- structural reification --> intrinsic HO
  -- total defunctionalization --> flattened FO family theory
  -- represented encoding --> raw SMT `declare-datatypes` commands
```

with user-defined inductive datatypes. The result must preserve the current proof
boundary: the final theorem concerns the reified intrinsic sentence. Reification
certifies that the Lean declaration and term have the recorded structure; it does
not silently introduce a denotation for arbitrary `Lean.Expr`.

## 1. First supported fragment

A **datatype instance** is one fully applied, monomorphized Lean inductive type,
such as `Option Int` or `Tree Bool`. A **datatype block** is the set of mutually
recursive instances that must appear in one SMT `declare-datatypes` command.

The first certified fragment will support:

- inhabited, productive inductive types in `Type`: every sort in a mutual block
  must have at least one finite constructor tree;
- no indices (`numIndices = 0`);
- all type parameters instantiated by ground types before reification;
- constructor fields with first-order, non-`Prop`, non-function types;
- enumeration, product, record, recursive, and directly mutually recursive
  datatypes;
- constructor applications, equality, quantification, selectors, and testers;
- datatype values crossing the existing defunctionalization boundary, including
  functions that accept or return datatype values;
- one native, monomorphic SMT datatype declaration per instantiated block.

Initially excluded:

- empty inductives, whose empty Lean carrier conflicts with SMT's nonempty sorts;
- indexed families such as `Vector α n`;
- dependent constructor fields and dependent elimination;
- function-valued fields;
- nested or indirect recursion through a datatype outside the emitted mutual
  block, such as `Rose` containing `List Rose` when `List` is declared separately;
- general recursors, induction principles, and arbitrary pattern-match lowering;
- user-defined recursive functions, which are separate from datatype structure;
- quotients, coinductive encodings, and proof-valued fields.

This mostly matches the structural subset already recognized by
`Translation.isSupportedDatatypeApp`. Its current “at least one constructor”
check must be strengthened to block productivity: for example,
`inductive Loop | mk : Loop → Loop` has a constructor but no finite Lean value.
Later phases may enlarge the fragment, but must not weaken its rejection checks.

## 2. Current gap

The typed datatype description, canonical finite-tree semantics, flattened
symbol ownership, native SMT command semantics, and shared model-lifting theorem
are now formalized. Lean reification retains one dependency-ordered environment,
and the opt-in production path atomically emits and records each exact certified
native datatype command.

The remaining gap is production-level whole-run composition. The semantic side
now constructs one dependency-folded target, proves each native datatype command
when its block is installed, and carries all of its laws through every later
disjoint block. `EnvRepresentation.lifted_valid` therefore validates the whole
native datatype prefix in the final target from one explicit dependency-order
certificate. The exact recursive `wf_T` definitions and integer graph used by
the `Nat` guard are also proved separately. Production still must construct the
shared FO representation and ordering certificate, combine the datatype and
guard graphs, and relate the surrounding legacy commands to the pure VCG command
array. Thus `crush.datatype.certify` certifies the datatype component, not the
entire extensible production translation.

## 3. Chosen proof shape

Keep `Ty.base` as the common sort reference and add a separate, typed datatype
environment. This avoids making arrow erasure and the core term syntax depend on
Lean metadata while still distinguishing opaque bases from declared datatypes.

The proposed proof-facing vocabulary is:

- `DataEnv`: an ordered collection of monomorphic datatype blocks;
- `DataDecl`: one datatype sort in a block;
- `CtorDecl`: one constructor and its ordered field sorts;
- `DataRef`, `CtorRef`, and `FieldRef`: typed references into those declarations;
- `DataVal`: the finite, well-founded constructor trees generated by a `DataEnv`;
- `DataSymbol`: typed constructor, selector, and tester symbols;
- `DataTrace`: the exact ordered native datatype commands represented by a run.

Opaque base sorts remain model-provided. A sort registered in `DataEnv` is instead
interpreted by the canonical free algebra `DataVal`; it is not an arbitrary
carrier accompanied by a few axioms. This matters for recursive datatypes: finite
first-order axioms for injectivity, disjointness, and exhaustiveness can still
admit non-well-founded or cyclic models, whereas SMT-LIB datatypes denote finite
well-founded values.

Constructors, selectors, and testers should remain typed family symbols at the FO
level so `FO.FamilyTerm` needs no datatype-specific term cases. Their symbol kind
must nevertheless be retained by the representation layer:

- constructors and selectors are declared by `declare-datatypes`, not again by
  `declare-fun`;
- a tester is encoded as the indexed identifier `(_ is <constructor>)`;
- a selector is constrained only on values made by its own constructor; SMT
  leaves its value on other constructors unspecified.

The extension should use native datatype commands, not replace them with an
uninterpreted encoding plus axioms. The raw SMT DSL remains untyped; datatype
correctness belongs in its relational semantics and the typed representation
relation.

## 4. Dependency-ordered worklist

Each checkbox is an implementation-sized task. A phase is complete only after
its exit condition and tests hold.

### Phase 0 — freeze the semantic contract

- [x] Record the exact first-fragment acceptance predicate independently of the

- [x] Decide the representation of recursive field descriptions accepted by

## 5. Theorem inventory

Names are provisional and intentionally short. Each theorem must state the
datatype environment explicitly or inherit it from its model.

| Layer | Proposed theorem | Required claim |
|---|---|---|
| Datatype core | `DataEnv.lookup_unique` | one sort has at most one datatype owner |
| Datatype semantics | `ctor_inj` | equal values of one constructor have equal fields |
| Datatype semantics | `ctor_ne` | values of distinct constructors are unequal |
| Datatype semantics | `ctor_cases` | every datatype value has one declared constructor |
| Datatype semantics | `sel_ctor` | a matching selector returns its constructor field |
| Datatype semantics | `test_ctor` | a tester recognizes exactly its constructor |
| HO/FO | `dataSymbol_denote` | every typed datatype symbol has its canonical meaning |
| Defunctionalization | `translate_denote` | datatype terms preserve denotation with all other terms |
| Defunctionalization | `model_extension` | each source model extends to the complete FO theory |
| SMT representation | `data_rep_sound` | a typed datatype block satisfies its raw native command |
| SMT representation | `representation_sound` | the full represented theory has a raw SMT model |
| VCG | `run_represents` | the stateful command array is the exact representation |
| VCG | `run_unsat_implies_source_unsat` | raw semantic unsat reflects to the intrinsic source |
| Guarded VCG | `runGuarded_represents` | the native, derived, and guarded array is exact |
| Guarded VCG | `runGuarded_unsat_under`, `runGuarded_unsat_implies_source_unsat` | raw unsat reflects under a custom model-indexed contract or, with one uniform interpretation, over every datatype-lawful source model |

No theorem in this list claims that cvc5 is correct, or that arbitrary
`Lean.Expr` has the same denotation as the intrinsic term. Those remain separate
trust boundaries.

## 7. Milestone gates

1. **Intrinsic gate:** Phases 0–4 prove datatype-aware defunctionalization without
   mentioning concrete SMT syntax.
2. **Representation gate:** Phases 5–6 prove native datatype command semantics and
   raw-model lifting.
3. **Lean gate:** Phases 7–8 connect exact Lean metadata and production command
   allocation to the certified route.
4. **Parity gate:** Phases 9–10 cover guarded fields, examples, docs, and CI.

Each gate should merge with `lake build` green. Avoid a long-lived branch where
the main soundness theorem is temporarily replaced by an axiom, `sorry`, or a
weaker uninterpreted encoding.

## 8. Open extensions after the first fragment

- General pattern matches can be lowered to testers and selectors once the
  match compiler's structural correspondence is certified.
- Recursor and induction support requires a separate theorem about recursive
  definitions or induction, not merely datatype declaration correctness.
- Nested datatypes need a declaration dependency analysis capable of forming a
  legal combined SMT block or a proved alternative encoding.
- Indexed inductive families need an erasure or refinement scheme for indices,
  well-formedness invariants, and dependent constructor/result typing. They are
  not a small extension of monomorphized algebraic datatypes.
